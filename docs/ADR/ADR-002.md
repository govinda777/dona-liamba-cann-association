# ADR-002: Governança como Código (IaC/GitOps) para a DAO Dona Liamba via Foundry, Safe e Snapshot em EVM L2

* **Status:** Aprovado
* **Data:** 25 de Agosto de 2026
* **Decisores:** Gov, Levi, Ale
* **Contexto Técnico:** Automação, reproducibilidade e governança descentralizada para a iniciativa Dona Liamba.

---

## 1. Contexto e Declaração do Problema
Para lançar a DAO da Dona Liamba sem dependência de interfaces manuais ou custos imprevisíveis de infraestrutura, é necessário que **todo o processo de criação de contratos, custódia compartilhada, distribuição de tokens e configuração do espaço de votação seja gerenciado como código (Infrastructure as Code - IaC / GitOps)**.

A arquitetura precisa atender aos seguintes requisitos:
1. **Suprimento Fixo:** Exatamente 100 tokens de governança (`$LIAMBA`).
2. **Split Inicial Automatizado:**
   * 50% (50 tokens) para a Tesouraria da Comunidade.
   * 50% (50 tokens) distribuídos entre os desenvolvedores construtores: Levi (16,66), Ale (16,66), Gov (16,68).
3. **Custo Operacional Reduzido:** Deploy em L2 EVM (Base ou Polygon PoS) e votações com **zero custo de gás** para a comunidade.
4. **Reproducibilidade e Auditoria:** Scripts declarativos, versionáveis e executáveis via pipelines de CI/CD (ex.: GitHub Actions).

---

## 2. Decisão Arquitetural
Adotar a stack **Foundry + Safe + Snapshot** em rede EVM L2 (**Base** ou **Polygon**):

```
       ┌─────────────────────────────────────────────────────────┐
       │             Repositório Git (IaC / GitOps)              │
       └────┬────────────────────────────┬──────────────────┬────┘
            │ (1) Deploy Declarativo     │ (2) Multi-Sig    │ (3) Space Settings
            ▼                            ▼                  ▼
   ┌─────────────────┐          ┌─────────────────┐   ┌─────────────────┐
   │ Foundry Script  │          │ Safe Proxy      │   │ Snapshot API    │
   │ (ERC-20 + Split)│          │ (2-de-3 sign)   │   │ (Off-chain Gas) │
   └────────┬────────┘          └────────┬────────┘   └────────┬────────┘
            │                            │                     │
            ▼                            ▼                     ▼
     100 $LIAMBA Mints ──────────► Treasury Safe       Votação Ponderada
     ├─ 50 Community              (Levi, Ale, Gov)     (Saldo de $LIAMBA)
     ├─ 16.66 Levi
     ├─ 16.66 Ale
     └─ 16.68 Gov
```

## 3. Especificação Técnica e Implementação IaC

### 3.1. Contrato do Token de Governança (`DonaLiambaToken.sol`)
Token ERC-20 padronizado utilizando OpenZeppelin com 2 casas decimais (facilitando a granularidade exata de 16,66):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/token/ERC20/extensions/ERC20Permit.sol";

contract DonaLiambaToken is ERC20, ERC20Permit {
    constructor(
        address treasuryCommunity,
        address levi,
        address ale,
        address gov
    ) ERC20("Dona Liamba Governance", "LIAMBA") ERC20Permit("Dona Liamba Governance") {
        // 2 decimais: 1 token = 100 unidades mínimas
        // Total = 100 * 10^2 = 10_000
        _mint(treasuryCommunity, 50 * 10**decimals()); // 50.00 LIAMBA
        _mint(levi, 1666);                             // 16.66 LIAMBA
        _mint(ale, 1666);                              // 16.66 LIAMBA
        _mint(gov, 1668);                              // 16.68 LIAMBA
    }

    function decimals() public pure override returns (uint8) {
        return 2;
    }
}
```

### 3.2. Script Declarativo de Deploy em Foundry (`DeployDAO.s.sol`)
Script em Solidity executável via CLI para orquestrar o deploy e a verificação no explorador de blocos:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Script.sol";
import "../src/DonaLiambaToken.sol";

contract DeployDAOScript is Script {
    function run() external {
        uint256 deployerPrivateKey = vm.envUint("DEPLOYER_PRIVATE_KEY");

        address treasury = vm.envAddress("COMMUNITY_TREASURY_SAFE");
        address levi = vm.envAddress("WALLET_LEVI");
        address ale = vm.envAddress("WALLET_ALE");
        address gov = vm.envAddress("WALLET_GOV");

        vm.startBroadcast(deployerPrivateKey);

        DonaLiambaToken token = new DonaLiambaToken(
            treasury,
            levi,
            ale,
            gov
        );

        vm.stopBroadcast();

        console.log("DonaLiambaToken deployed at:", address(token));
        console.log("Total Supply:", token.totalSupply());
    }
}
```

## 4. Consequências

### Positivas
* **Imutabilidade e Transparência:** Nenhum token adicional pode ser cunhado além das 100 unidades definidas no construtor.
* **Custo Zero para Votação Comunitária:** O Snapshot utiliza assinaturas criptográficas baseadas no padrão **EIP-712** off-chain; os membros da comunidade não pagam taxas de rede (gas) para participar das decisões.
* **Segurança na Tesouraria:** A alocação da comunidade (50 tokens) e eventuais fundos operacionais ficam sob controle de um cofre Safe multi-sig (exigindo quórum de 2-de-3 assinaturas entre Levi, Ale e Gov).
* **Auditabilidade e GitOps:** Toda a topologia da DAO pode ser reconstruída ou simulada em redes de teste (Sepolia) ou mainnet de maneira transparente a partir do repositório Git.

### Negativas / Mitigações
* **Dependência de Indexação Off-chain:** O Snapshot depende de nós RPC públicos ou dedicados para ler os saldos das carteiras no momento da proposta (*snapshot block*).
  * *Mitigação:* Usar endpoints RPC redundantes configurados no espaço do Snapshot.
* **Execução Não-Automática de Propostas:** Votações no Snapshot sinalizam o consenso da comunidade, mas a execução de transferências na tesouraria de forma manual exige a assinatura de 2-de-3 dos fundadores no Safe.
  * *Mitigação:* O módulo Zodiac (SafeSnap) pode ser acoplado futuramente se houver necessidade de uma execução on-chain totalmente automatizada e descentralizada.

## 5. Jornada do Usuário Leigo e Transparência (UI/UX)

Para garantir que a governança seja acessível a todos os associados, independentemente de conhecimento técnico prévio sobre Web3, a interface e a comunicação seguirão as seguintes diretrizes:

### 5.1. Transparência Jurídica e Propósito Formal
A interface do "Hub da Comunidade" (espaço da DAO) deverá ostentar de forma clara e ininterrupta, tanto no cabeçalho quanto no rodapé da página, o seguinte *disclaimer*:

> *"Esta área do site tem como objetivo exclusivo trazer total transparência sobre o funcionamento dos processos internos, governança e decisões organizacionais da DAO Dona Liamba."*

Este aviso reforça a prestação de contas no modelo B2B (pacientes, médicos e associações).

### 5.2. Passo a Passo da Jornada do Usuário
O fluxo do usuário (associado) foi projetado para abstrair as complexidades da blockchain:

1. **Acessar a Plataforma (Login Simplificado):**
   * O usuário acessa a DAO por meio do item "Comunidade DAO" no menu principal do site.
   * A autenticação é feita via **Privy** (infraestrutura de smart wallets), permitindo o login rápido via e-mail ou redes sociais, abstraindo a criação de carteiras e o gerenciamento de chaves privadas.
2. **Consultar Poder de Voto:**
   * Um dashboard unificado exibirá visualmente o saldo de tokens de governança (`$LIAMBA`) atrelado à conta do usuário, traduzindo o saldo bruto em seu peso real nas votações.
3. **Interagir e Votar:**
   * O espaço exibirá as propostas ativas e encerradas puxadas via API do Snapshot.
   * O usuário poderá votar de forma intuitiva com **zero custo de gas**, utilizando assinaturas off-chain simplificadas.
4. **Acompanhar a Execução:**
   * O usuário poderá visualizar de forma unificada o estado atual da Tesouraria (Safe Multi-sig).
   * Relatórios automáticos e status das propostas demonstrarão como as decisões tomadas pela comunidade orientam a execução das transações pela diretoria.
